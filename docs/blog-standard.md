# 胖大喵 Blog 發文規範

適用於這個靜態 landing page，不是 Odoo 重建專案。維護順序：先寫來源 → 生成／預覽 → 檢查 → 編輯覆核 → 核對發布授權才發布 → 核對線上結果。目前暫定每週三篇，建議週一、三、五，台灣時間；週末留給補資料，不為湊數換日期或發未查證文章。這是編輯節奏，不是搜尋平台的要求；尚未設定自動發布。

## 來源與統一 HTML

- 新文章在 `content/blog/<slug>.md`。正文使用 Markdown，不手刻整頁 HTML；文章模板統一語系、文章標題、作者日期、社群分享資訊與 `BlogPosting`。既有兩篇舊文沿用目前網址；非必要不更換 slug。若需改網址，另外安排舊網址轉向與驗證。
- 文章發布後，正式網址採 `/blog/<slug>/`。生成器維護新文 HTML、Blog 列表和 sitemap；不要只手改生成檔。編輯內容與發布產物分離。GitHub 若為公開 repo，儲存在 repo 的草稿即使不上站也可能被讀到；未公開商品、私人照片或其他敏感稿件不可寫進公開儲存庫。
- 首篇貓砂盆量法目前只是驗證稿，使用原創 AI 封面插畫與原創量測圖，皆非商品實拍。發布前核對品牌署名和日期；若要加入店內商品數字或照片，先拿實物尺寸、量法及可公開圖片，未取得就不寫成品牌實測。

## 指令與發布順序

首次使用 Node.js 24.x，於專案根目錄執行 `npm ci --ignore-scripts`。

| 指令 | 用途 |
| --- | --- |
| `npm run blog:preview -- <slug> <temp-directory>` | 在系統暫存目錄預覽單篇。輸出目錄須為新的或空的暫存子目錄；不把 URL、產物或狀態寫回公開網站。 |
| `npm run blog:build` | 生成或更新可發布的靜態頁、列表和 sitemap。檢查生成檔 diff，不要手動補其中一個檔案。 |
| `npm run lint` | ESLint 檢查 Blog 產生器、模板模組與測試的 JavaScript；不檢查 HTML 標籤或生成結果。 |
| `npm run blog:check` | 唯讀檢查原稿、公開產物與連結，檢查後無須回復任何生成檔。 |
| `npm run blog:test` | 執行回歸測試，包含故意造錯的案例。 |
| `npm run blog:stage` | 驗證後將允許公開的靜態檔放入 `dist/`，不包含 Markdown、草稿、規範或測試。 |

新文檔首需填 `slug`、`status`（預設工作流程先寫 `draft`，不省略）、`title`、`description`、`category`、`author`。草稿可先填 `cover`（`/assets/blog/` 下）和 `coverAlt` 供覆核；正式發布必須有封面兩欄及真實的 `publishedAt`（YYYY-MM-DD）。實質修訂時可填 `updatedAt`，有作者專頁才填 `authorUrl`。Slug 用小寫 ASCII 字母、數字與連字號，並和檔名相同。

稿件覆核通過且批准上線後，才把 `status` 改成 `published`，填正式資訊、重新 build/check 並提交生成結果。優先走分支與 PR，確認 CI 結果；未確認 GitHub 要求此檢查、Vercel 正式分支與輸出目錄設定以前，不當作已具備部署攔截。若用 Vercel，應部署 `dist/` 而不是 repo 根目錄；不得把整個目錄直接拖曳上傳，避免稿件外流。

## 每篇的驗收證據

| 關卡 | 必查項目 | 留下的證據 |
| --- | --- | --- |
| 自動檢查 | 驗證原稿欄位、日期與 slug；檢查實際 HTML、圖片、站內連結、返回列表、canonical／結構化資料／sitemap 一致，並確保草稿不在部署輸出。 | 本版檢查指令、CI 結果；預期失敗的回歸測試也要能重現。 |
| 編輯覆核 | 一文回答一個真實問題；定題後先審搜尋意圖、相近文章和本站差異，再決定大綱。開頭給結論，小標、步驟、表格或 FAQ 只在有幫助時加入。使用台灣繁中；產品數字可追溯，圖片有授權，引用能支持原句。未驗證不得當作實測，不捏造獸醫署名或安全保證。確認手機版與連結。 | [每篇研究單](blog-research-template.md)、文章預覽、實測／來源證據、圖片權利和覆核需修事項。 |
| 上線確認 | 核對部署版本與審查版本。正式部署確認後先驗一次，再於 10 分鐘後重新讀取正式文章、Blog 列表對應頁與 sitemap；文章須為新版本、HTTP 200、非 noindex，列表卡片要連到正式 canonical。若動到蝦皮追蹤連結，同時比對正式頁輸出的 href（不製造測試購物點擊）。 | 正式網址、已部署版本、首次及 10 分鐘後的檢查時間與結果；Search Console 未收錄或無權限就分別寫「待收錄」或「未驗證」。 |

來源連結要在文章預覽逐一確認能開到支持原句的內容，而不只查搜尋摘要或 HTTP 狀態。相同證據有可直接閱讀的網頁時，優先用網頁，不用大型 PDF 下載轉址。

以正式環境確認部署成功的時間開始算 10 分鐘，不從寫稿、合併或送出部署開始算。排定複查後才回報進度；若複查仍是舊版、缺卡或 404，先確認部署與快取狀態，明確告知尚未驗收，不報發布成功。例行稿由維護者依本規範審，不請站主逐篇審。

CI 能擋機械錯誤，不能替代編輯覆核。以新增／改動文章為人工覆核範圍；模板變更另抽樣既有頁面與新頁。發文不得因收錄或 AI 引用還未發生而偽報已完成，亦不得以 SEO 名義堆關鍵字、重複內容或只改時間戳。

## 制式出稿：篇幅、圖、連結

1. **一篇解一個問題。** 開頭先回答，接著放步驟／差異、必要的適用條件、來源和下一步。按搜尋意圖和必答項目定篇幅，不以本站舊估稿範圍或同業字數當上下限。想估稿時，可只數相同題型的可見正文，以繁中漢字數的中位數作參考，排除頁首、導覽、商品推薦模組、圖片 alt、留言和來源清單；樣本不足或題型混雜就不比。這不是 SEO／AEO／GEO 權重、最低門檻或 lint。寫清楚就停，必要的例外不要為了篇幅而刪。[Google SEO 指南](https://developers.google.com/search/docs/fundamentals/seo-starter-guide) 沒有建議字數。
2. **每篇製作專屬封面，有量法或比較時再加內文圖。** 封面用新作插畫、實拍或經授權圖材，不沿用其他文章封面；舊素材只在確實有助說明時使用。新增圖片放 `assets/blog/<slug>/`，優先壓成 WebP，填具體 alt；有文字或步驟的圖在正文或圖說重述重點。插畫／AI 示意不能冒充商品照片、實測或獸醫證據；有尺寸、箭頭、文字時另對照內容、手機可讀性與來源。
3. **固定雙向入口，內文連結只放真的相關。** 正式 `/blog/` 列表自動加新文卡片，正式文章模板固定連回 `/blog/`。文內挑相關舊文或分類，用描述清楚的連結文字；舊文有延伸閱讀價值時補回鏈，不設硬性連結數。草稿預覽可去正式 Blog，但正式 Blog 不列草稿。程式驗收列表、回鏈、站內網址、sitemap、圖片資產；編輯覆核連結是否真的有用。

### 提到自家商品時

- **只用已登錄的連結。** 先在 [蝦皮追蹤清單](../scripts/shopee-links.json) 核對品名、賣場編號、規格與文章用途。商品必須在使用者提供的清單內，不以同類商品、蝦皮首頁或關聯款假冒同一商品。沒有對應連結時，先不放商品按鈕；有新連結就先更新主清單再引用。本批來源是 2026-11-23 提供的蝦皮表格。
- **在 Markdown 使用清單代號。** 例如 `[看看胖大喵的長通道掀蓋款](shopee:cat-litter-box-102)`。由產生器帶入「帶追蹤碼的連結」欄位原值，不用「活動名稱」或「追跡參數」欄重組，不改大小寫、不自行新增或移除參數。複製表格時去除 SVG 圖示、Markdown 跳脫等呈現雜訊，不把它們混進網址。靜態 HTML 裡的 `&amp;` 只是跳脫，讀者點擊仍是 `&`。
- **用讀者看得懂的文字。** 後台代號、規格代碼和選項備註留在商品資料庫，不直接搬進正文。多規格賣場不宣稱會預選；真的要區分不同規格時，優先用讀者能辨認的款式名或外觀。蝦皮首頁只放在店鋪入口，不拿來當特定商品的替代連結。
- **先交代為什麼值得點。** 前一段要先回答讀者的困擾，講設計怎麼幫忙、有什麼取捨，才放對得上這個情境的商品連結。換成任一商品仍然說得通，或刪掉前一段也不影響連結出現的理由，就重寫或刪掉。延伸配件不是文章主題時，最多順帶提醒，不硬加第二個導購連結。
- **先答問題，再放商品。** 自家商品連結就明示是胖大喵賣場；若只是看結構，標為款式參考。外徑、商品頁宣稱、體重或型號不能替代實測內徑、個別適用性或航空公司接受條件。缺證據就不寫「適合」「已實測」「保證」，不用清單本身當產品證明。
- **規格先查資料庫，不直接從商品標題搬進文章。** 自家商品按同一代號查 [商品資料庫](shopee-products.md)。公開頁量的是什麼、哪個型號、證據日期和待核處都要能追到。標成待核或規格互相矛盾的數字不引用；若要用實測，另外留日期、量測位置、單位、型號與照片。價格、庫存及贈品不靠舊資料表。
- **分開驗收。** Lint 檢查清單及實際連結是否一致；人工覆核 CTA、款式、主張是否相符。可用時另檢查手機／桌面落地頁，以及從蝦皮後台確認實際歸因；本機通過不代表蝦皮已收到轉換。

### 推薦／比較文可以放其他品牌

- 自家商品只用核准的蝦皮追蹤網址；這不限制其他品牌入選。其他品牌優先連其官網或官方商品頁，不加胖大喵 UTM，不把別人的商品換成自家或店鋪入口。
- 先定同用途、同情境的比較標準，再挑選商品；例如砂盆比開口、可用內部空間、拆洗和資料是否齊全，不因品牌而換標準。比較文若有合適的其他品牌，就放進同一欄位比。自家款品名自然寫「胖大喵」，不假裝第三方背書；若有分潤或合作，清楚標示。表格註明實測或只比公開規格。缺資料就標「未公布／未實測」，不猜、不打假分，也不硬宣稱誰第一。
- 只有自家商品或缺乏可靠的可比規格時，寫成單款介紹、選購方法、或只比較有依據的部分，不叫「全品牌推薦／實測評比」。教學文不硬塞排行榜。

### 選購文怎麼寫得好選、好信任

1. **先用情境縮小選擇，不先丟一排商品。** 第一段說明誰要先看哪個條件，再給一張簡表或一個步驟。選項多不一定不好；當規格難比較、讀者還不知道自己要什麼時，先定淘汰條件，比硬湊固定款數更有用。[選擇負荷的條件](https://myscp.onlinelibrary.wiley.com/doi/10.1016/j.jcps.2014.08.002) · [整體效果與研究差異](https://bear.warrington.ufl.edu/brenner/mar7588/Papers/scheibehenne-jcr2010.pdf)
2. **把不好判斷的規格放在同一張尺上。** 砂盆同欄比入口淨寬、門檻、可用底面和拆洗，單位和量的位置一致；內徑與外徑不能並排當同一項。「加大、好清理」改寫成可看懂的結構或拿得出證據的差異，圖片也要幫讀者做同一個判斷。[並排評估實驗](https://pages.ucsd.edu/~cmckenzie/Hsee1996OBHDP.pdf)
3. **優點和有關的限制放在一起。** 說這款在哪個情境有用、哪個條件下不必選。不要硬塞假缺點或只挑對自家有利的欄位。雙面說法可能影響可信度，但研究不是寵物電商轉換保證。[雙面廣告統合分析](https://ucrisportal.univie.ac.at/en/publications/two-sided-advertising-a-meta-analysis/)

文章可用「直接答 → 選購門檻 → 同規格比較或量測圖 → 哪種情況不要選 → 自然的下一步」。不是每篇都要有表格或推薦。這些是編輯原則，不能代替品牌自己的成效驗證；上線後分開觀察文章點擊與實際商品導流，不拿不同主題的轉換率直接推論寫法有效。

## 可重複的錯誤要變成 lint 規則

從 Review、發文、改版或上線核對找到**可能再發生、而且可用客觀條件判斷**的錯誤時，不只修當次頁面：

1. 加一個最小回歸案例，重現原本漏檢的情況。
2. 文章、HTML 或發布產物的錯誤加進 `blog:check`，讓 CI 與部署 staging 一起擋；JavaScript 本身的錯誤優先用 ESLint 的適用規則。錯誤訊息要指出檔案和原因。
3. 驗證錯誤案例失敗、正常案例通過，再結案。既有規則已能擋下時只補缺少的測例，不做重複規則。

例：臺灣繁中草稿在粗體全形標點後緊接中文字，可能把 `**` 直接顯示給讀者。檢查會擋下這個已知形態；可在結束標記與下一個字間加空格，或分成兩句。刻意跳脫的星號與程式碼不受此規則影響。

例：舊文有兩個「返回 Blog」按鈕，第一版只要找到一個正確的就放行；現在逐一檢查，改壞其中任何一個都會失敗。若錯誤必須由人判斷（如來源不能支持主張、圖片授權不清），補進編輯覆核表及證據要求，不用機械 lint 假裝已驗證。

## 選題與知識查證

一週集中備稿一次，每週一、三、五暫排三個不同問題，週末留緩衝；開始前先準備兩週、六個題目，只有覆核通過的稿件可以進發布佇列。沒可靠依據或沒有新增價值就延後、有實質新證據才更新舊文，不由未驗證稿遞補。

### 定題後、寫稿前：看前五篇相近結果

1. **先寫讀者的問題，再選詞。** 一個主關鍵字及一到兩個台灣用語的變體，先記讀者是要答案、操作步驟、比較還是直接買。檢查站內既有文章有沒有回答同一問題；有就優先更新，不另開頁互搶。
2. **看查詢結果的組成，再篩前五。** 記下日期、查詢原文、搜尋來源與地區／語言設定（工具沒提供就記未確認）。先標記自然結果以文章、商品、分類或影片為主，再依當次出現順序選最先看到的五篇同意圖或最相近的可讀文章。去掉廣告、不相干結果、重複網域或轉載、不開放正文的頁面；不要把 PDF 指引和商品頁拿來比文章長度，但可靠的官方文件可以另外做事實查證。少於五篇可用一組變體補，標記原查詢與補樣來源；仍不足就註明實際篇數，不硬湊，也不把一次快照當成固定名次。用工具只看到摘要時不可記為「已讀」。
3. **每篇留下三件事。** 用自己的話記「它提供的答案／形式」、「讀者還可能卡在哪」、「這項觀察如何影響本站大綱」。有實際出現的延伸問題或相關搜尋可以收錄，未出現就記未觀察到，不把自己猜的問題寫成搜尋數據。若結果幾乎都是商品頁，先想是商品頁要補資訊，還是改用更明確的問句做文章。
4. **先決定本站能多做什麼。** 打開 [研究單範本和首篇示範](blog-research-template.md)，列至少一項有證據、能幫讀者做決定的新增價值，例如實測、原創示意圖、核對表或明確的例外。只吸收讀者需求，不複製人家段落順序、圖或文字。找不到新增價值就縮題、併回既有文章或停稿。前五篇用來推斷意圖，不是用來投票決定事實，也不當作發表用來源清單。
5. **審稿檢查研究單和成品對不對得上。** 確認必答項有寫到、差異有做出來，原始來源能支撐重要說法；配圖、內鏈和 CTA 要能幫讀者採取下一步。不用 lint 判斷競品是否相關或文章是否真的有價值。

## 成效怎麼看

先記錄發布前基線；每月按文章看自然搜尋曝光、點擊、索引與已配置的商品外連事件。若有權限，再分開記錄 Google AI 曝光、Bing 引用和 ChatGPT 導流；它們不是同一指標。用結果調整主題與更新順序，不以單篇或幾次人工 AI 搜尋判斷頻率。可使用 [Google Search Console](https://search.google.com/search-console/) 看搜尋成效、索引與 AI 報表，以及 [Bing Webmaster Tools](https://www.bing.com/webmasters/) 看 AI 引用；這些帳號尚未在本次驗收中連線。

不用 DA／DR 或假定字數加權當作 Google 權重。先確認可索引，再按頁面和查詢看曝光、點擊與 CTR，平均排名只當趨勢診斷；另看相關轉換。AI 引用不是排名，也不是流量。用同題型、相近上線天數比較，不把不同文章的差異直接歸因於字數。
